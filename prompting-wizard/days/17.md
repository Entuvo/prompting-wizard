# Day 17 — Output schemas: a shape a script can check

## Concept

"Give me the results in a nice format" describes a feeling. "Nice" isn't checkable — no script can verify it, so verifying the output means reading it end to end, by eye, every time you run the prompt.

A schema is checkable when it names every field, its type, and its order, and shows what an empty value looks like — filled with dummy data before a single real value exists:

```
[
  {"item": "example item one", "status": "pass", "note": ""},
  {"item": "example item two", "status": "fail", "note": "one-line reason it failed"}
]
```

Anyone reading this knows the payload is an array, each entry has three keys, status is one of two literal values shown here as "pass" and "fail," and an item with nothing to flag gets an empty string, not a missing key. A five-line script could reject anything that doesn't match — "list the results with a status and a note" can't be checked that way at all.

Here is the test: could you write a script that rejects a malformed output without you reading it first? If not, the schema is still a description, not a contract — fill it with dummy values until it is.

## Before / After

**Before**

> Give me the results for {{TASK}} in a nice format.

**After**

> Return the results for {{TASK}} as JSON matching this shape exactly — one object per item, dummy values shown to fix the contract, status always "pass" or "fail":
>
> ```
> [
>   {"item": "sample entry one", "status": "pass", "note": ""},
>   {"item": "sample entry two", "status": "fail", "note": "one-line reason it failed"}
> ]
> ```
>
> Do not add a key. Do not omit a key even when its value is empty.

"Nice" is unfalsifiable — anything tidy enough passes. The schema is falsifiable: a missing key, an extra key, or a status outside the two literals is a checkable failure, not a matter of taste.
