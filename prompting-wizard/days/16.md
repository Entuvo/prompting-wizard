# Day 16 — Few-shot examples: two that disagree

## Concept

One example shows the model what you want; it doesn't show what you don't. A single "here's a good one" pins the centre of the target and leaves every edge open — nothing told the model whether a borderline case counts, so it guesses.

Two examples that disagree do more work than ten that agree. A boundary case shows where the line actually sits, forcing the model to notice a line exists at all. A failure case shows something that looks like a match but isn't — the exact mistake an unguided model would make. Agreement teaches nothing new; contrast teaches the rule.

Choose examples like test cases, not decoration. The best boundary case is one you'd hesitate over yourself; the best failure case is one you've watched the model actually get wrong. Anything softer is padding.

Here is the test: could either example be swapped for a different instance of the same pattern without changing what the model would learn? If yes, it isn't earning its place — replace it with one that disagrees with the other.

## Before / After

**Before**

> Classify each item in {{TASK}} as urgent or not urgent.

**After**

> Classify each item in {{TASK}} as urgent or not urgent.
>
> Boundary case: latency crept from 200ms to 350ms overnight, no alert fired, no user report. Not urgent — slow, silent, no threshold crossed.
> Failure case: a customer wrote in all caps with three exclamation marks about a typo in the footer copy. Not urgent — dramatic tone, but the impact is cosmetic.

No examples left the line between the two categories to guesswork. The boundary case shows a quiet, easy-to-miss non-match; the failure case shows something that looks like a match on tone alone but isn't — the exact false alarm an unguided model would raise.
