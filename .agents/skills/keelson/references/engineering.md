# Prove engineering changes

Load the relevant section for a bug, refactor, recurring failure, migration, stateful change, or review concern. Routine edits keep existing proportionate checks. This guide owns regression and refactor proof; [verification](verification.md) owns receipts and [review](review.md) owns independent Opus review. Extend the existing brief/checkpoint rather than create another mandatory packet. Evidence can remain in approved private records outside the engineering root.

## Reproduce bugs before fixing

Distinguish a reported defect from newly requested behavior using the existing accepted contract and source. Tests for a new requirement can fail against the original implementation without proving a historical regression. Label that evidence as a new-behavior baseline in the reply and project records; claim an existing bug or regression only when the prior contract or history supports it. A user calling a change a “fix” does not itself establish that history.

1. Identify intended behavior from accepted requirements, actual behavior, affected caller, and smallest observable trigger. Trace the mechanism through callers and state. Instrument uncertainty instead of guessing. After restart failures, inspect persisted state, configuration, caches and locks before changing code.
2. Where an existing cheap test target fits, add a focused regression and run it before production edits. Confirm failure demonstrates the reported defect, not missing setup or an unrelated exception. A passing test has not reproduced the bug.
3. If a useful test requires disproportionate infrastructure or brittle mocks, use the closest executable reproduction: a command, API request with readback, browser action, or captured-output comparison. Do not create a large harness for a small fix. Record why failing-before evidence is unavailable if it cannot be obtained; keep that gap explicit.
4. Fix the cause within scope. Search for the same faulty pattern and assess affected siblings. Necessary boundary validation remains; a guard or retry that merely hides a broken internal contract does not establish a fix. Record out-of-scope instances without silently expanding work.
5. Repeat the original trigger against the fix, then relevant nearby checks. Preserve failed-before and passing-after output, source identity, command, and limitation. Do not delete existing work to manufacture a red baseline, weaken expectations to match a defect, or report a failed receipt as qualification.

For flaky behavior, control the causal input where possible and record repetitions and residual uncertainty. A single lucky pass does not prove the race is fixed. Report `trigger / mechanism / before evidence / after evidence / remaining gap` in the existing record.

## Pin behavior during refactors and migrations

Before structural edits, inspect the affected contract and run a characterization test, snapshot, or old-versus-new equivalence check. Types and lint alone do not pin behavior. Separate newly discovered bugs or behavior changes from the refactor; changes to accepted behavior return to the appropriate intake/delivery decision.

Name the simpler target shape and intended reduction in reader effort. Remove proven dead paths, redundant decisions and unnecessary wrappers before adding structure. Reuse [architecture](architecture.md) for new or complex design choices; moving a local function does not itself require panels. Move in verifiable units, holding the behavioral pin at each declared boundary. Reject speculative reshaping that adds indirection without a concrete benefit.

For an internal API migration, inventory direct callers, dynamic/string references, tests, examples, docs and back-references. When there are no external compatibility obligations and coordinated change is feasible, migrate all callers and delete the old API in the same wave. Verify actual files after renames. Any necessary temporary adapter needs a reason, owner, removal condition and bounded follow-up; do not silently turn it into permanent dual behavior. External consumers or stored-data compatibility require an explicit migration contract instead of unconditional deletion.

Planned rewrites may declare temporary breakage only inside isolated, reversible phase boundaries. Name affected checks, recovery point and the first fully coherent boundary before starting. Retain useful checks while moving, verify each completed unit before dependent work, and run required static and runtime checks for the entire affected migration at completion. Never release a broken intermediate state or mark known breakage as passing. Preserve unrelated work; do not reset or rebase a user's checkout just to obtain a tidy sequence.

For nontrivial repeated edits or difficult analyses, reuse or build the smallest rerunnable transformation/check. Prove it against the first inspected unit, make reruns safe, and retain the tool with the evidence. Prefer one deterministic transformation to workers hand-applying the same recipe. A couple of obvious edits need no generator. If commits are requested, order them so a reviewer can follow baseline, change and proof; this guide does not itself authorize commits or PRs.

## Assert behavior that can fail

Exercise the subject through its real consumer entrypoint and compare concrete output or observable effects with an independently derived expectation. Verify persistence, authorization boundaries and side effects where they define success. Prefer runnable dependencies; when mocks are necessary, assert meaningful payload/state and state the integration limit.

Ask whether a plausible defect, removed operation, or empty result would still pass. If yes, strengthen or remove the check. Mere invocation counts, truthiness, prompt substrings, duplicated constants, self-comparison, or fixture-only assertions do not prove behavior. Pair an absence assertion with a case that demonstrates the operation can produce the expected presence. Keep useful relational/schema consistency checks and compile-time assertions, but label their narrower scope. Use a targeted mutation or controlled faulty case when assertion sensitivity remains uncertain; do not add mutation machinery to every routine edit.

## Encode recurring corrections and challenge premises

Capture corrections and unexpected failures in existing records, classifying one-off, recurring, or systemic. On a repeated instruction or correction, inspect whether a type construction, lint/CI rule, canonical helper, or boundary/runtime check can enforce it. Use the strongest proportionate mechanism, prove it rejects the known failure and accepts valid behavior, and replace redundant instructions with a link to that owner. If judgment prevents enforcement, retain a clear example and concrete follow-up owner; recording alone does not close the issue.

When two fixes sharing a premise fail the same gate, stop the next compensating fix. Write the shared premise, competing causal hypotheses and a discriminating executable check. When the symptom involves allocation, role assignment or state imbalance, create a rerunnable census per actor, not just a total, and compare runs. Persistent skew points to the rule assigning the role; inspect that rule before adding pools, retries or rebalancing. Test removing or changing the assignment when evidence supports it. An even census does not support the skew hypothesis: record that result and investigate another cause. Complex redesign follows architecture; the census grants no wider scope.

## Model boundaries, state and consumers

For new logic, choose data structures against actual access patterns before adding branches. Integrate changed requirements through affected types, callers, examples and rationale. Keep useful foundations ahead of dependent features, after removing obsolete code. Centralize repeated decisions; question signal threading through several layers when a direct interface would suffice.

Parse untrusted inputs once into domain values at each trust boundary. Keep wire/storage representations private and business decisions separate from I/O. In typed code, represent meaningful variants explicitly, exhaust them, distinguish semantic identifiers where confusion is possible, and derive types from the authoritative schema. Strengthen types where an otherwise partial operation demands proof, not for speculative precision. In TypeScript, prefer `unknown` plus validated narrowing to `any`, unchecked casts or non-null assertions; validate type guards themselves. Use existing schema tools rather than invent a second schema system. Where supported, `satisfies`, schema-derived types and an exhaustive `never` check retain compiler evidence. Prefer named object arguments when positional values obscure meaning, subject to measured hot-path constraints. Reuse structured diagnostics with useful operation identifiers and secret redaction; remove ad hoc debug output from shipped code. External API choices still follow delivery's versioned documentation requirement.

For retryable state changes, name operation identity, partial states, reconciliation and ownership. Check a second execution and interruptions at meaningful mutation boundaries. Re-execution must converge without duplicating effects or deleting another actor's resources. Inspect stale state and locks with actual ownership/liveness evidence; PID or filename similarity alone can be insufficient. If several actors mutate state, remove unnecessary sharing first. Give independent facts separate owned records. Where a single mutable object is required, enforce serialization with a single writer, transaction, lock or compare-and-swap; prose conventions are not concurrency control.

Review from the consumer's perspective, including API callers and maintainers. Prioritize the accepted core journey and understandable success/error behavior over implementation convenience or extra options. For UI decisions use Impeccable. For code, reduce both layers readers must trace and hidden mutable state they must hold; remove pass-through wrappers, narrow mutation scope, and derive values rather than synchronize duplicates when safe. Keep helpful abstractions that hide real decisions. Simplicity never removes required validation, accessibility or security.

## Scope review lenses and preserve constraints

Supply Opus the relevant contract, surrounding callers/state, and proof. Ask only applicable lenses: correctness and errors, root cause, integration, data/ownership fit, behavioral evidence, consumer experience, justified complexity, and security. Security findings must trace a reachable input through the dangerous operation or authorization check, with concrete impact. Inspect secrets in selected logs and outputs, race/TOCTOU paths and boundary validation where relevant; unsupported hypothetical warnings are not findings.

When touched code contains suppressions or workaround comments, or an audit is requested, include a scoped independent review. Inventory exact rule/value, source location, claimed constraint and evidence. Trace historical rationale when needed via [investigation](investigation.md). Fix an accepted underlying defect within scope, then remove the obsolete suppression/comment. Retain necessary external constraints and explanatory rationale. Do not blanket-delete comments, disable rules to pass, or erase safety constraints whose cause remains unresolved. Encode enforceable constraints with the smallest authorized check; otherwise report the unenforced constraint and owner. Reject unsupported reviewer claims with evidence and retain the disposition in the review packet.

For documentation changes, identify the reader's task and choose a clear procedure, reference, tutorial or explanation. Use exact project terms, explicit actors and unambiguous conditions. Cut unsupported claims, filler and repeated synonyms while preserving needed context. Avoid arbitrary file-size bans, mandatory editorial sweeps or source-style purges.
