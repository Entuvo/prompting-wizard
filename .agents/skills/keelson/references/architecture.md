# Architecture: ground, compare, synthesize, implement

Required for new projects and complex changes after confirmed intake and before dependent implementation. Restores pstack's [architect](upstream/pstack/architect/SOURCE.txt) and [arena](upstream/pstack/arena/SOURCE.txt) method, adapted through [Codex host rules](codex.md). Bundled upstream files are unchanged source evidence, not active host instructions. Do not inherit Cursor tool names, model aliases/fallbacks, automatic commits, or extra permissions. Keelson's exact Opus review and authorization rules prevail.

## Choose the route

Record classification and concrete reason in the current plan/brief; no separate classification form.

| Route | Trigger | Required work |
|---|---|---|
| Architecture | New product/project without an applicable reviewed design; new subsystem; changed public contract, domain/data model, ownership, trust boundary, persistence, concurrency, cross-service integration, or consequential stack choice; repeated workarounds expose a wrong design | Ground affected scope, at least two structurally distinct candidate sketches, independent comparison, synthesis and current Opus design review before dependent implementation |
| Routine | Local edit or mechanical change that preserves established contracts, boundaries, data ownership and architectural shape; uncertainty can be resolved by local inspection/checks | Reuse existing structure, make the smallest supported change, run proportionate checks; no candidate panel or pre-build architecture review. Normal independent delivery review still applies |
| Resume | Required architecture artifacts and exact Opus review exist and their decision inputs remain applicable | Reuse them; do not regenerate candidates or ask for settled approval. Inspect interrupted work and continue authorized implementation |

File count is not the trigger: a one-file change can alter a trust boundary, and a multi-file rename can be routine. When a routine change reveals an architectural trigger, stop only dependent implementation, record new evidence, and route affected scope through architecture. Unaffected authorized work continues. Unknown product intent returns to intake; do not design around an assumed answer. A deadline does not waive the architecture contract.

## Ground

Read confirmed product/feature brief, operating limits, actual source, existing decisions and deployment constraints. Trace a representative caller-to-result path and ownership/invariants across affected boundaries, including failure and persistence behavior. For changed ownership/layering, inspect history or prior rationale and record what is known versus unresolved. Greenfield work skips existing-code tracing only; requirements and constraints still ground the design.

Identify decision inputs by paths and hashes (including relevant manifests/lockfiles, brief, constraints, source and recorded observations). External facts also need observation date/context and refresh conditions; unchanged source hashes alone cannot establish current provider behavior. Reuse the [documentation evidence contract](delivery.md#ground-implementation-in-documentation) for external API choices. Resolve factual uncertainty with a bounded research question/prototype and stopping condition; preserve throwaway output as evidence, not production acceptance.

## Carry applicable deliverables through the package

In the existing plan/brief, connect each requested outcome and applicable capability to its deliverable, source inputs, verification evidence and current disposition. Reuse existing acceptance rows; do not create a second tracking system. Assess whether ownership/data boundaries, admission/recovery order or other relationships need [diagrams](diagrams.md). If useful or requested, include their actual artifact paths and semantic/static/rendered review obligations in the package. If a diagram is not useful, record the concrete reason briefly. A user-requested deliverable cannot be excluded merely because text was reviewed.

Use completed, blocked, unverified or not-needed-with-reason (or existing equivalents). Missing files, stale diagrams and missing visual checks remain open. A proposed path or promise is not an artifact. This accounting is for applicable architecture/delivery work; routine edits do not acquire a diagram, panel or new checklist.

## Compare actual alternatives

Before runners start, define the artifact and 3–6 concrete comparison criteria, including interface depth (complexity hidden behind a small public surface) and ease of extension without breaking invariants; make the remaining criteria task-specific. Write at least two structurally distinct sketches, not cosmetic variants. Compare real alternatives; a candidate ruled out by a constraint records that reason rather than pretending feasibility. Lack of an easy alternative is not permission to skip exploration or invent a straw man.

Use independent native candidate workers when available and authorized, each owning separate output files and receiving the same confirmed task/grounding plus the [runner prompt](upstream/pstack/architect/references/runner-prompt.md) as source evidence. Every candidate brief must prepend the following host adaptation before the upstream material:

> Produce exactly one candidate sketch. Keelson’s architecture and Codex host rules govern this assignment; upstream material is design guidance only. Do not run architect/arena as a coordinator, spawn workers, or delegate further. Ignore upstream Cursor dispatch, model aliases/fallbacks, commit instructions and assertions that runners use different models. Record only your actual host-reported model identity; if unavailable, say unknown. Do not infer model diversity. Read only supplied/available principles; list missing named principle skills as unavailable, never invent their contents. Apply the self-contained design discipline in this brief and the supplied runner text. Write only your assigned candidate artifacts; do not inspect other candidates or choose the final base.

The lead must supply the confirmed task, grounding, output path, actual available references and this preamble together; a bare upstream runner prompt is not a valid assignment. Keep the comparison rubric private to the lead and independent judge; do not include it or lead preferences in candidate briefs. Candidates receive the shared design disciplines above, not the task-specific scoring criteria. Two candidates are the minimum; add more only for justified independent directions within budget/capacity. Use available host models, record actual identities, and do not claim multi-model diversity when workers share one model. Candidates do not see other candidates or the lead's preferred answer. Do not launch the architecture panel recursively inside candidate workers: their assignment is one sketch, not running the coordinator workflow.

Each candidate supplies:

- Caller-first usage and 2–3 realistic call sites, followed by types, signatures and module map; stub bodies/pseudocode, not a premature implementation.
- Domain structure and dominant access patterns. Apply [Model the Domain](upstream/pstack/principle-model-the-domain/SOURCE.txt): state machine, typed model, registry, reducer or another fitting structure; justify the choice, do not force abstraction.
- Ownership, invariants, validation/trust boundaries, shared writes, idempotency/recovery and failure paths relevant to this scope.
- A short rationale using the [upstream template](upstream/pstack/architect/references/rationale-template.md), with its synthesis section left for the lead. Screen [design red flags](upstream/pstack/architect/references/design-red-flags.md): shallow modules, information leakage, temporal decomposition and pass-through layers.

For a new or reconsidered stack, the Keelson brief/rationale additionally records candidate technologies/versions, requirement fit, deployment/operations, compatibility, migration/reversibility and cost constraints that affect this project. Compare material alternatives using evidence, not popularity. Preserve user-selected stack constraints; do not broaden authorization or change them silently. Reuse settled choices without forcing a new stack contest. This stack evidence requirement is a Keelson adaptation, not a claimed upstream stack-selection algorithm.

## Judge and synthesize

Once candidate files are stable, a fresh independent reviewer compares them against the rubric and recommends a base. Reviewer must not have authored a candidate and receives task, constraints, rubric and candidate artifacts, not lead rankings. Native read-only review is sufficient for this comparison; actual model and scope are recorded. The lead independently reads and scores every candidate, then reconciles disagreement with the reviewer using reasons/evidence. A vote or shared model agreement is not proof.

Pick the viable base with the strongest interface depth and easiest extension without breaking invariants; prefer a cleaner boundary or smaller API when candidates otherwise tie. Incorporate useful parts deliberately, keeping one coherent design. Record base choice, per-criterion comparison, independent verdict, accepted grafts, rejected alternatives, trade-offs, risks, and first verifiable implementation step. Unresolved material disagreement needs investigation or another bounded comparison, not silent suppression. Product choices return to the user; routine engineering choices within confirmed intent and limits do not need another approval.

Run [exact independent Opus review](review.md) on the final synthesized design and its candidate/rubric/grounding evidence before dependent implementation. This pre-build gate is Keelson's fixed-review adaptation of pstack's design comparison, separate from its later implementation review. Include the applicable-deliverables accounting, actual artifacts and proof/exclusions, alongside acceptance criteria. Ask the reviewer to check package completeness against the brief and applicable guidance, not only correctness of supplied text. Include actual API excerpts/evidence where relevant; tool-disabled Opus cannot follow unsupplied links. A comparison of candidates alone cannot approve a subsequently changed synthesis. Fix material findings and refresh review against the final inputs. Review readiness is not user acceptance or deployment permission.

If native candidate/comparison tools are unavailable, produce separate sequential candidate packages and disclose loss of independent generation; do not label self-comparison independent. First send only task, constraints, rubric and candidate artifacts to Opus for independent comparison, excluding lead rankings and synthesis. Record that comparison, reconcile the lead’s separate assessment, then synthesize. Use a separate Opus call to review the final synthesized design and its evidence. Do not combine the blind comparison and final-design review into one call. If required Opus, decisive evidence or a material product decision is unavailable, architecture remains blocked/unverified for dependent implementation; continue permitted research and unrelated work. Do not silently drop alternatives, substitute a reviewer or fabricate completion.

## Artifacts and implementation

Use the project's existing private records root and current plan. Default for a new unrestricted project: `.keelson/architecture/<unit>/` containing grounding/input hashes, rubric, `candidate-a/`, `candidate-b/`, independent comparison and a synthesized sketch/rationale. Small designs can combine the text sections in one file; keep candidate independence and review evidence distinguishable. Link exact review receipt from the current plan/checkpoint. Use existing ADR conventions for consequential decisions instead of creating a competing authority. This package is design evidence, not runtime proof.

A current package requires all applicable deliverables accounted for and inspected, all required stages, a ready/non-stale Opus receipt for final design, and unchanged applicable decision inputs. Supplied API/observation refresh conditions must also hold. Record changed requirements, newly discovered dependency files and changed assumptions even when old review file hashes still match. When a depicted boundary changes, reconcile the affected diagram and its checks even if an older text-review receipt remains hash-current. Reopen only affected design decisions; then review changed synthesis before dependent implementation. No human architecture checkpoint by default beyond confirmed intent and existing limits; honor an explicitly requested checkpoint.

Reconcile each affected explanation of a changed boundary: grounding, candidate-specific ownership/concurrency, operator contract, diagrams or tables, and current handoff. Do not leave an old shared claim where candidates now differ. Preserve prior inputs and hash lineage when recording an authorized amendment; existing user instructions can supply that authorization without another approval. Refresh applicable manifests/checks after reconciliation, keeping historical review scope distinct. This is targeted consistency work, not a new panel for a routine correction.

Implement against the chosen usage/types/boundaries. Surface deviations instead of silently widening interfaces. Repeated same-shaped workarounds, type escape hatches, unexpected shared-state locks or callers depending on hidden internals trigger re-grounding and fresh alternative sketches. A single ordinary edge case is not automatic redesign. Preserve existing work while superseding the faulty sketch. Finish with real behavioral checks and independent implementation review; design approval cannot substitute for either.

For undocumented rationale or downstream safety claims, use [investigation](investigation.md). Apply conditional [engineering invariants](engineering.md) when validating the sketch. Imported SOURCE.txt files retain original bytes and relative source links as historical text; active adapted guidance and the self-contained candidate brief govern execution.
