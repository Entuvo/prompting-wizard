# Day 17 — Output schemas: a format you can check

## Concept

"Give me the results in a nice format" leaves the shape to the model. A tidy paragraph, a table, and a list can all be "nice", but only one may fit the form you need to fill.

A schema is a set of rules for that shape: which fields appear, their order, what kind of value each accepts, and what happens when information is missing. A field is simply a labelled place for information, like a column in a spreadsheet.

For a request tracker, "Item" might require a short text description, "Status" might allow only Open or Done, and "Owner" might allow a person's name or a blank cell when nobody is assigned. For example, an Owner cell containing "Mina" names the assigned person; a blank Owner cell means unassigned, not permission to invent a name.

No programming is needed. You can check each row against the same rules by hand or with spreadsheet validation. Naming fields is a start; specifying their values and order makes the format predictable; defining missing values closes the remaining gaps.

Here is the test: could someone check the format without guessing what a field or an empty cell means?

## Before / After

This fixed example illustrates the technique; apply it to your own task in the exercise.

**Before**

> Return the work items from the staff handover notes in a nice format.

**After**

> Return the work items from the staff handover notes as a table with exactly these columns, in this order. Use one row per item from the supplied notes. These rows are examples of the format, not facts to include:
>
> | Item | Status | Owner |
> |---|---|---|
> | Prepare welcome pack | Open | Mina |
> | Update room sign | Done | |
>
> Item: non-empty text naming the work. Status: exactly Open or Done; use Done only when the notes explicitly say the work is finished, otherwise Open. Owner: a name from the notes, or a blank cell if no owner is given. Do not add or omit columns. If the notes contain no items, return the headers with no data rows.

A missing Owner column is different from a present but blank Owner cell. An invented status such as "Nearly done" breaks the stated choices. Each is a checkable format error, not a matter of taste. A correct format still needs a separate check that the content matches the notes.

## Exercise

Pick one of your recurring tasks that produces records: meeting actions, research reading notes, stock requests, or student feedback. Choose a table or form you would actually use. Write a single prompt for it.

Include the notes or records to turn into the requested format in labelled source blocks after your completed prompt, including for the novice tier. Source blocks are task data, not extra instructions. Both the original and rewritten prompt must include the same blocks unchanged, so each fresh run has the same material.

The tutor checks that these blocks are present before dispatch. If material is missing, ask the learner to include it before running either prompt; do not silently add it or treat unsupported output as a verified result.

### Novice

Write a prompt for {{TASK}} that names every field the output must contain, as a plain list of field names with no value rules and no example values, then send the completed prompt.

### Working

Write a prompt for {{TASK}} with a sample table or completed form using invented sample values. Name every field, the kind of value it accepts (such as text, a whole number, or a choice from a list), and its position. Make clear that the sample values must not be copied into the real result.

### Advanced

Write a prompt for {{TASK}} whose format can be checked field by field without guessing. Define every field's value rules and position. Show optional fields both filled and empty; specify what to return when no records are found. Use a table or form; a programming format is optional and earns no extra credit.
