# Day 27 — Failure diagnosis: test the cause against evidence

## Concept

A disappointing result is an observation, not yet a diagnosis. The prompt may omit an artifact, goal, or boundary. The model may also lack source material, encounter a tool failure, or reach a capability limit.

Name one plausible cause and the evidence supporting it before changing anything. For a prompt defect, name the lever or technique. For denied file access, name the access failure; adding prompt detail will not repair it. A correct diagnosis can leave the prompt unchanged.

Choose a focused test of that cause. Changing several unrelated factors at once makes improvement hard to explain. State what would weaken your hypothesis and what remains uncertain.

Here is the test: does the proposed change address the failure shown by the evidence, and can the comparison distinguish that cause from alternatives? Do not manufacture a prompt fault when the evidence points elsewhere.

## Before / After

**Before**

The tutor asks the learner for a real prompt of theirs that failed — one that produced output they had to discard or heavily rework. If the learner has none ready, the tutor reads `## Log` in `PROGRESS.md`, finds the scored day with the lowest `rubric` score — most recent, if several tie — names that day to the learner, and asks them for the prompt they used that day. If `## Log` has no scored day either, ask the learner for any prompt of theirs that disappointed them; if they cannot supply one, stop and resume the lesson when they can rather than inventing a failure. The log line records the day's topic and its score, not the prompt itself, so the learner supplies it. Either way, the failure is real; nothing here is invented.

**After**

The learner names, in writing, one plausible cause, with supporting evidence and any uncertainty — before anyone touches the prompt or runs anything. Where the tier also asks for a fix, the change they'd make goes in the same writing, still before anything runs. Only after that prediction is recorded does the tutor run the original prompt if it hasn't already been run, confirm what actually broke, and check whether the learner's diagnosis, and any fix, targeted the thing that was actually wrong.

## Exercise

Ask the learner for a real failed prompt, or use the lowest-scoring `## Log` entry, per `## Before / After`, before presenting a tier.

### Novice

Have the learner locate the failure in the actual output or tool evidence and name one plausible cause before changing anything. Run the original only when the necessary inputs and authorized access exist; otherwise record the missing prerequisite. No fix today.

### Working

Have the learner name one evidence-supported cause and a focused fix or test for it, then run the original prompt, if not already run, to confirm the diagnosis before applying the fix.

### Advanced

Have the learner diagnose one cause and test only the implicated factor. Keep other conditions equivalent and state remaining confounders. A tool or context repair may leave the prompt unchanged; obtain normal authorized access before rerunning.
