# Day 23 — Agent and tool prompting: tools, timing, and done

## Concept

"Use the tools to sort out {{TASK}}" names no tools, no timing, and no stop condition. Naming tools without saying when each applies still leaves the model guessing whether the third search was needed or the fifth edit was one too many.

A prompt clears the middle rungs once it says which tool serves which situation and when. What separates strong from merely adequate is whether "done" can be gamed: "stop when you've made a change" is satisfied by a change that does nothing useful, while "stop when the tests pass and you can point to the fix" can't be satisfied by motion alone.

Stating the condition before the tools is a useful habit, not a scored one — tools listed first with an airtight, ungameable condition after them score no lower.

Here is the test: read your done-condition and ask how a model could satisfy it without doing the real work. If you can answer that, close the hole — restate the condition so the shortcut no longer counts as done.

## Before / After

**Before**

> Use the tools to sort out {{TASK}}.

**After**

> Stop when {{TASK}} passes its existing checks and you can point to the specific change that fixed it. Until then, use the search tool to find the failing area, the edit tool to change it, and the test tool to verify — in that order, one change at a time.

Every scored property is now present: which tools, when each applies, and a stop condition tied to a state you can check against the transcript — passing tests and a located fix — instead of a claim the agent could satisfy by going through the motions.

## Exercise

Pick one of your recurring tasks. Write a single prompt for it.

### Novice

Write a prompt for {{TASK}} that names which tools to use and their rough sequence, but gives only the vague stop condition "stop when it is done." Leave that condition vague in the prompt you send.

### Working

Write a prompt for {{TASK}} that states which tools to use, when each applies, and a specific done-condition that motion alone can satisfy, such as stopping after one change. State how that condition could be gamed, but do not close the hole in the prompt you send.

### Advanced

Write a prompt for {{TASK}} whose stop condition is un-gameable. State one way a model could satisfy it without doing the real work, then rewrite the condition so that shortcut no longer counts as done.
